# Issue #1 — Gmail UI XML / Gmail API の条件同等性判定

## 現状（2026-10-27）

`gmail_filter_deployer.py` の `build_template` は XML の `from: a OR b` を
`criteria.query: {from:a from:b}` に変換し、`subject: {x y}` は
`criteria.query: subject:{x y}` に変換する。
`hasTheWord` は `(...) ` で囲い、`canonical_template` は条件の文字列について両端空白除去にとどめる。
`counter` / `delta` / `tokens_digest` はテンプレートのハッシュに依存する。

このため、Gmail が条件を別のフィールドや構文で返すと、
実際の検索結果が同じであっても追加と削除の両方が発生し得る。
一方、テキストが似ているだけでは検索意味論が同じとは限らない。

## 判定ポリシー

1. **証明済みの同等性**のみ正規化し、配備前後で同じ正規化を使う。
2. **未証明の候補**は差分を勝手に消さず、監査で明示する。実際の配備前に別途安全性を確認する。
3. **明らかに異なる条件**は通常の差分のままとする。
4. 自動同等判定が追加・削除対象、最終照合、承認済み計画の進捗・ハッシュに及ぼす変更は一括で検証する。途中配備計画の意味を新しいアルゴリズムで無断変更しない。
5. `Action/Delete` と `Trash` のグループ承認、最終承認、削除先行の配備順序、途中復旧を保持する。

## 確認対象と必要な証拠

| ケース | XML → API の例 | 現時点の扱い | 確認方法 |
| --- | --- | --- | --- |
| 送信元 OR | `from: a OR b` → `query: {from:a from:b}` | 同等性候補 | Gmail UI と API の両形式で同じ対象メールにマッチすることを検証 |
| 件名 OR | `subject: {x y}` → `query: subject:{x y}` | 同等性候補 | 日本語、空白、複数語を含む実例で検索意味論を照合 |
| 括弧 | `(in:spam ...)` → `((in:spam ...))` | 同等性候補 | 否定と OR を含む式でグループ化の意味が変わらないことを検証 |
| 引用符と空白 | `"two words"` や前後スペース | 原則保留 | 引用句を分割・再配列・無差別トリムしない |
| 否定 | `doesNotHaveTheWord` / `negatedQuery` | 原則保留 | AND/OR との結合を含めて検証 |
| 真の条件変更 | 宛先、差出人、件名、処理ラベルの相違 | 非同等 | 追加・削除が消えないことを回帰テスト |

### 作業順

1. 実アカウントを変更しない read-only 診断を追加し、元条件・API条件・差分の分類・件数をローカルの非公開ログに保存する。
2. 個々の変換を合成フィクスチャと必要な Gmail 検索照合で検証する。証明できなければ正規化しない。
3. 条件正規化を一箇所に実装して、差分表示・配備・検証・再開に同一の比較規則を使用する。
4. 既存の保留計画との互換性を確認し、移行できない場合は安全に停止する。
5. `run` / `verify` と回帰テストで削除・追加件数の減少、真の差分の保持、全カテゴリの承認順序を検証する。

## 既存運用との整合

2026-10-26 の実測では、複数件 Batch は単独リクエストより速くならなかった
（`docs/reports/2026-10-26-filter-add-batch.md`）。
この課題では送信方式を変更しない。通常送信は1件ずつ、全件照合は原則50操作ごとを維持する。
