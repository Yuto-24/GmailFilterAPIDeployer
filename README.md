# Gmail Filter API Deployer

Gmailに現在登録されているフィルタと、最新版Master XMLとの差分を照合して配備するCLIです。Docker Composeに対応します。

## 最短の運用：配備は1コマンド

最初に1度だけ`local/credentials.json`（Google Cloud OAuth DesktopクライアントJSON）、`.env`（Gmailアドレス）を用意します。Master XMLは`local/masters/`に**元のファイル名のまま**保存します。旧Masterやリネームは不要です。

```bash
cp .env.example .env
# .envの GMAIL_EXPECTED_EMAIL を自分のアドレスに変更
mkdir -p local/masters
# local/credentials.json および local/masters/mailFilters_v0.14.0_proposed_master_20261019.xml 等を配置
docker compose build
```

以後は毎回、以下の**1コマンドだけ**実行します。

```bash
docker compose run --rm --service-ports deployer run

# フィルタごとの処理内容も表示するとき
# docker compose run --rm --service-ports deployer run -v
```

実行内容は **XML検証 → OAuth認証・アカウント照合 → 差分計算 → 基本の件数表示 → Action/Delete全件表示・グループ承認 → Trash全件表示・グループ承認 → 最終確認 `[y/N]` → 配備 → API照合** です。

**承認の順序は基本 → Action/Delete → Trash → 最終確認**です。基本（Type・Service・Org等）は個別承認せず、最後の全体承認に含めます。基本の詳細は`run -v`で表示できます。DeleteとTrashの差分は`-v`なしでも、追加・削除する全ルールの条件と処理を表示します。条件変更はGmail API上の旧ルール削除と新ルール作成として表示します。該当差分がないカテゴリの確認は省略します。

Action/DeleteとTrashはそれぞれ`[y/N]`で承認または見送れます。見送ったグループはGmailの現行ルールを維持します。**実際のGmail変更は、最後の全体確認に`y`と入力した後にのみ開始**します。`n`・Enter・Ctrl+Cは配備しません（ただし、すでに変更が始まっている配備の再開確認は別です）。

`--approve`および`--allow-removals`は`run`では不要です。初回OAuthでは表示URLをブラウザで開いて認証します（ホスト側ローカルポート`127.0.0.1:8765`）。TTYを使えない環境（`-T`、CI、パイプ等）では自動承認しません。

**Gmailの1000フィルタ上限対策：** 新規配備計画では、最終承認後に**旧フィルタを先に削除し、次に新フィルタを追加**します。現行846件・削除257件・追加341件なら、846→589→930件となり上限を超えません。削除と追加の間には一時的に旧振り分け条件がない時間帯が生じます。配備は既定で1件ずつ実行し、Gmail APIで照合しながら、途中中断時も承認した手順の進捗から再開します。過去の追加先行方式で実行中だった計画は、その実行順序のまま再開します。表現差による不要な差分の最適化は [Issue #1](https://github.com/Yuto-24/GmailFilterAPIDeployer/issues/1) に分離しています。

**Gmail APIの読戻しが一時的に不一致の場合：** 削除後または追加の検証タイミングで期待したフィルタ集合と一致しなければ、**次の変更操作を行わず**、2秒、5秒の待機を挟んで最大2回の追加読取り（計3回）を行います。期待するルール集合が完全一致した場合のみ続行します。なお、3回とも不一致・未対応のAPIエラー・外部変更の場合は停止し、承認済み計画とログを保持します。これは成功した書込み後の読戻し照合です。書込み自体が失敗した場合は、次の復旧手順を使います。

不一致を検出した際は、**最初の読戻し結果を含めて毎回** `local/logs/diagnostics/batch_*.json` に時刻・期待状態・実フィルタID・ルール内容・不足ID等を保存します。不一致が後で解消しても、診断記録は保持されます。診断ファイルは個人情報を含むため、公開リポジトリ等にはアップロードしないでください。

**フィルタのバッチ処理：** 既定は1件ずつの逐次処理です。複数件バッチは明示的に選択できますが、部分成功やサーバー側エラーが起きる可能性があります。原因不明の400を一時障害として自動再送することはしません。既存バッチ計画の再開経路ではエラー後の読戻しを保存して停止します。新規の逐次処理でも400等の失敗直後に実設定を読み戻して停止します。復旧用読取りが失敗したら、その場で停止し記録を保持します。

明示的に`--batch-size 2`〜`25`を指定すると、削除・追加をそれぞれ指定件数ずつ1回のHTTPリクエストにまとめます。送信件数と全件照合の間隔は独立しており、全件照合は通常50操作ごとです。50件境界をまたぐバッチは分割します（例: `--batch-size 20` は20・20・10件で照合）。1回の全件照合にはラベル一覧とフィルタ一覧の2要求を使います。バッチ内部の並列実行は保証されないため、接続タイムアウトは60秒、応答の読取りタイムアウトは60秒×送信件数です。APIの使用量は内部の操作数で計上されるため、クォータが減るわけではありません。

バッチ内の実行順は保証されないため、削除と追加は別のバッチに分け、削除先行／旧版の追加先行順序を維持します。ラベルは追加バッチの前に作成します。`--batch-size 1`は従来の逐次処理ですが、既にバッチで開始した計画も、同じ進捗形式を維持して通常の単独HTTP要求で再開します。この再開経路では失敗後の読戻し・停止を維持し、自動再送はしません。[Googleのバッチ仕様](https://developers.google.com/workspace/gmail/api/guides/batch)（最大100操作、推奨50以下）。

`--max-batches N`を`run`または`apply`に付けると、最大Nバッチを実行・読戻し照合した時点で終了します。未完了なら保留計画と進捗を保持し、再開時は確認済みの操作を繰り返しません。この上限は複数件バッチ、または既存バッチ計画の再開専用です。既存バッチ計画の少量確認には`run --batch-size 1 --max-batches 1 -v`を使用できます。新規・従来の逐次計画で`--batch-size 1`と併用すると最終承認前に停止します。既存バッチ計画の単独HTTP要求は1件を1バッチとして数えます。ラベル作成はバッチ数に含みません。

**バッチの部分失敗・応答消失・中断：** 送信前に対象操作・削除ID・その時点の期待状態を計画別ログへ原子的に保存します。各成功応答も個別に保存します。正常な応答の後は期待状態を更新して次の要求へ進みますが、照合時にID・内容が一致しなければ後続要求を止めます。失敗時には実設定を読戻し、2秒・5秒後にも照合して進捗を記録して停止します。Googleのエラー理由・状態・メッセージもローカルの進捗ログに記録します（リクエストヘッダーや認証情報は記録しません）。バッチ全体や失敗操作を自動再送しません。同じ`run`を再実行すると、保存済みバッチの任意の部分成功（先頭から順番に成功していなくても可）をID・内容で照合し、最終承認後に未反映の操作だけを送信します。未送信の操作や既存IDに外部変更があれば停止します。通常の読戻し不一致は`local/logs/diagnostics/batch_*.json`にも直前・観測時の設定を保存します。復旧用読取り自体が失敗した場合はその場で停止します。

既存の逐次処理で中断した計画も、承認内容と実行順を変えずバッチ処理へ移行できます。バッチを始めた後は新しい進捗形式が必要なため、完了まで旧版へ戻さず、保留計画と進捗ログを両方保持してください。

中断した場合は`local/run_pending.json`に固定した計画に対し、現在のGmail設定がその計画の途中状態であることを検証して再開します。別の変更が見つかった場合は停止します。計画ごとのログは`local/logs/`に保存するため、**翌週の新しい配備でもログをリネームする必要はありません**。計画全文は`local/run_plan.json`に保存されます。`local/`と`.env`はGit管理対象外です。

## 全件照合の間隔と進捗の意味

`run` / `apply` は開始・再開時、通常50変更操作ごと、削除と追加の工程切替時、終了時に全フィルタ・ラベルを照合します。末尾が50件未満でも照合します。新規ラベルは50件ごと、およびフィルタ追加へ進む前にも照合します。`--max-batches`による途中終了も、未照合の末尾を照合してから返ります。最後の工程の照合結果は終了時の確認・結果表示に再利用し、直後に同じ一覧を取り直しません。

- 送信前のintentと各成功応答は、照合間隔にかかわらず毎回原子的に保存します。
- `acknowledged_add` / `acknowledged_remove` は応答等で確認した進捗、`completed_add` / `completed_remove` は全件読戻しで確認した進捗です。画面にも両方を表示します。`verified=true` は最終照合まで完了した状態です。
- `batch_checkpoint.rows` は成功応答から組み立てた期待状態を含みます。`readback_confirmed=false` の間は実設定との全件一致が未確認です。未処理のintentは`pending`に残り、再開時に必ず実設定と照合します。
- 失敗・応答不明時は次の操作を止め、その時点で実設定を読み戻します。逐次処理の同一操作に対する有界リトライと、既存バッチ計画の読戻し後停止は従来どおりです。復旧読取りが失敗したら、さらに書込みや入れ子の再試行を行いません。
- 旧逐次計画・旧バッチ進捗からも、承認済みの操作と順序を維持して再開できます。再開で既に全操作の反映を確認できた場合も、ジャーナルを照合完了に更新してから保留計画を解消します。

**外部変更は次の全件照合まで検知が遅れます。** 毎操作で外部ドリフトを検知する保証ではありません。実行中はGmail UIや別クライアントでフィルタ・ラベルを編集しないでください。同名・同内容でもIDが変わった設定、予期しない追加・削除、ラベル変更は照合時に停止します。

`tests/test_cadence.py` の合成88操作（削除45・追加43、ラベル作成なし）では、同じ実行処理の照合間隔1と50を比較し、変更要求88回を維持したまま一覧取得が178回から6回になりました。HTTP要求合計は266回から94回（約64.7%減）です。これは照合頻度の比較で、実Gmailでの時間短縮率ではありません。

運用判断の根拠: [追加Batch実測報告と再利用できる知見](docs/reports/2026-10-26-filter-add-batch.md)。配備の送信は引き続き1件ずつが既定です。

## 一時的なAPI障害からの復旧

以下の自動再試行は、逐次処理（`--batch-size 1`で開始した計画）とラベル作成に適用します。フィルタのバッチは上記のとおり読戻して停止し、再開時に未反映分を処理します。

フィルタの削除・作成、ラベル作成がHTTP 500/502/503/504・429・一時的な通信障害で失敗した場合は、**同じ操作をすぐに再送せず**、ラベル・フィルタの実設定を再取得します。403は`rateLimitExceeded`／`userRateLimitExceeded`だけを一時障害として扱い、権限不足・API無効・日次上限等は再試行しません。

- **実行済みの次状態に完全一致**：反映済みとして進捗を記録し、重複作成・再削除を避けます。件数やルールだけでなく、既存フィルタIDとラベル名・IDも照合します。削除を見送ったID不明のルールは内容と件数を別に保持・照合し、他の承認済み操作を妨げず、そのルール自体は変更しません。
- **実行前の状態に完全一致**：1秒、2秒を基準にそれぞれ0〜1秒のジッターを加えて待ち、待機後にも再取得・照合してから再試行します。API書込みは最初の試行を含め**最大3回**です。待機中に反映済みになれば再送しません。
- **どちらにも一致しない／復旧用の取得APIが失敗**：後続の変更を停止します。復旧用の取得APIは再試行せず、保留計画と進捗ログを保持します。

通常のラベル・フィルタ読取りAPIにも、同じ一時障害分類と最大3回の有界バックオフを適用します。認証・OAuth処理の自動再試行は追加しません。SDK内の無条件リトライは使いません。通信は`AuthorizedSession`経由で、単独リクエストの接続・読取りのタイムアウトを各60秒とし（バッチの読取りは上記の件数比例）、通信層の自動再送・リダイレクト・401後の自動再送も無効にします（送信前の通常のトークン更新は維持します）。

`-v`では失敗した操作・HTTPステータスまたは例外種別・待機秒数・試行回数を表示します。計画別ログには`api_error`、`reconciled_before_retry`、`reconciled_after_error`、`reconciliation_failed`と操作・step・時刻を保存します。停止後は`local/run_pending.json`、Master XML、進捗ログを保持したまま、同じ`run`コマンドで実設定との照合と最終確認を経て再開します。途中の状態から`plan`を作り直したり、進捗数を手で修正したりしないでください。

これらは観測できた状態に基づく復旧であり、Gmail側の読取り一貫性や外部クライアントとの排他を保証するものではありません。配備中の手動フィルタ編集は避けてください。バッチ内の変更がすべて同時に確定する保証はありません。次のバッチへ進む前に全体を照合します。

一時障害とバックオフの根拠：[Gmail APIのエラー処理](https://developers.google.com/workspace/gmail/api/guides/handle-errors)。

## 削除対象の事前検証と一部未適用

最終承認前に、削除予定ルールがGmail API上のフィルタID1件に一意に対応するか検証します。0件（存在しない）、複数件（重複）、ID欠落は「スキップ予定」として明細を表示します。特定できないルールは削除せず、他の承認済みルールは処理します。

スキップしたルールは承認済みの有効ターゲットに残し、配備後もMasterとの完全一致と区別します。スキップによって1000件上限に達する場合は最終承認前に原因を表示します。最終承認直前にはGmail実設定を再取得して、差分取得時点から変更がないか照合します。

配備完了後には追加・削除成功・スキップ・Masterへの未適用差分を表示します。外部から途中で設定が変わり、処理済み状態を確定できない場合はそれ以上の変更をせず、途中計画を保存します。

## `deployer`以降のCLI仕様

`docker compose run --rm --service-ports deployer <subcommand> [options]` の`deployer`はComposeのサービス名、`<subcommand>`以下はPython CLIの引数です。`--service-ports`はDocker Composeのオプションで、初回OAuth認証を行うコマンド（`run`/`plan`）で使います。認証済みでも付けたままで問題ありません。

| サブコマンド | 意味 | Gmailへの変更 | 使用例 |
|---|---|---|---|
| `run` | 検証から承認・配備・検証まで一括 | `y`でのみ変更 | `... deployer run` |
| `validate` | XML構文・処理内容の静的検証 | なし | `... deployer validate` |
| `plan` | 実フィルタから差分計画を保存 | なし | `... deployer plan` |
| `apply` | 保存された`plan.json`を厳格に適用 | あり | `... deployer apply --approve HASH --allow-removals` |
| `verify` | 実フィルタとMasterの一致を確認 | なし | `... deployer verify` |

### `run`：推奨

- `--target PATH`：バージョン自動選択を使わず、対象Master XMLを明示。
- `--batch-size N`：削除・追加をまとめるHTTPバッチ件数。**1〜25、既定1**。1で開始した計画は逐次処理になります。
- `-v`, `--verbose`：フィルタ単位の処理結果や照合状況に加え、API読取・削除・追加の開始/終了時刻（UTCオフセット付きISO 8601）と所要秒数を標準出力に表示。エラー発生時にも失敗した処理と経過時間を表示します。承認待ちを含む`run`全体と配備処理のみの所要時間も分けて表示します。実行結果の保存先は従来どおり`local/logs/`です。Docker内タイムゾーンがUTCなら`+00:00`になるため、ホスト端末のJSTと時刻を比較する際はオフセットを考慮してください。
- `--expected-email ADDRESS`：`.env`の`GMAIL_EXPECTED_EMAIL`より優先するアカウント照合先。
- `--local-dir PATH`：Masterと配備記録の保存フォルダ。既定`/app/local`（Docker内）。
- `--client-secrets PATH`：OAuth DesktopクライアントJSON。既定`/app/local/credentials.json`。
- `--token PATH`：OAuth認証トークン。既定`/app/local/token.json`。

`run`に`--approve`/`--allow-removals`はありません。承認ハッシュは内部で作成・照合し、対話確認を行います。

### `validate`：オフライン検証

- `--target PATH`：検証対象を指定。省略時は最新Master。
- `--base PATH`：任意の旧Masterと比較し、Delete/Trash変更等を検出。
- `--out PATH`：検証結果JSONを保存。
- `--local-dir PATH`：Master検索先を変更。

### `plan`：詳細な配備計画

- `--target PATH`：配備先Masterを指定（省略時は最新版）。
- `--base PATH`：現行Gmailがその旧Masterと完全一致する場合だけ計画する、厳格モード。
- `--also-baseline PATH`：`--base`と同時に追加する既知Master。複数指定可。
- `--out PATH`：計画保存先。既定`/app/local/plan.json`。
- `--expected-email`、`--local-dir`、`--client-secrets`、`--token`：`run`と同じ。

### `apply`：上級者向け分割操作

- `--approve HASH`：`plan`の`approval_digest`を指定。**必須**。
- `--allow-removals`：旧フィルタの削除を伴う配備を明示的に承認。ない場合は削除対象があれば停止。
- `--plan PATH`：`plan.json`のパス。既定`/app/local/plan.json`。
- `--log PATH`：進捗記録。既定`/app/local/deploy_log.json`。
- `--batch-size N`：削除・追加のHTTPバッチ件数（1〜25、既定1）。
- `-v`, `--verbose`：`run`と同じ詳細表示。
- `--expected-email`、`--local-dir`、`--client-secrets`、`--token`：`run`と同じ。

### `verify`：配備後の完全比較

- `--target PATH`：照合対象Master。
- `--out PATH`：照合結果JSONの保存先（既定`/app/local/verify.json`）。
- `--expected-email`、`--local-dir`、`--client-secrets`、`--token`：`run`と同じ。

コマンドの全オプションは次で確認できます。

```bash
docker compose run --rm deployer --help
docker compose run --rm deployer run --help
docker compose run --rm deployer apply --help
```

## XML自動選択の規則

`local/masters/*.xml`と`local/*.xml`のうち、ファイル名に`vX.Y.Z`と`master`を含むファイルからバージョン・日付が最も新しいものを選びます。`patch`、`export`、`cumulative`、`incremental`、`baseline`、`target`は候補から除外します。同順位の候補が複数あれば停止し、明示`--target`指定を求めます。候補がない場合のみ旧`local/target.xml`を使います。

## トラブルシューティング：Gmail API無効（HTTP 403）

`Gmail API has not been used in project ... or it is disabled` / `accessNotConfigured` は**Google CloudのGmail APIが有効になっていない**ことを示します。エラー内のGoogle Cloudプロジェクトを選択し、[Gmail API](https://console.cloud.google.com/apis/library/gmail.googleapis.com)を有効化してから同じコマンドを再実行してください。反映には数分かかる場合があります。

これはOAuth同意やメールのラベル設定とは別の問題です。`[3/6] Gmailの現行ラベル・フィルタを取得中`で発生した場合は**配備処理は開始されておらず、Gmailフィルタは一切変更されていません**。スクリプトもこの原因を個別に表示するようにしてあります。配備が実際に開始された後で別のエラーが出た場合は、進捗ログと現在のGmail設定を確認してから再開してください。

## 安全上の制約

- 配備対象アカウントを`.env`の`GMAIL_EXPECTED_EMAIL`で固定し、実際にOAuthログインしたGoogleアカウントと照合します。指定がない場合は停止します。
- `Action/Delete`もMaster XMLに合わせて追加・削除・置換します。ただしDeleteは**ラベル付与のみ**で、既読化・スター・重要・Trashの複合操作は禁止です。Trash移動アクションもMaster XMLを正本として差分更新します。新Master内のTrashアクションは従来どおり`in:spam`条件に限定し、変更があれば全件と警告を最終確認前に表示します。既存Gmail側の余分なTrashフィルタは承認後に削除対象となります。自動Archiveは禁止します。
- UIベースのフィルタXMLをGmail API形式に変換できない条件、転送フィルタ等の予期しないアクション、1000件上限超過、途中状態不一致の場合は停止します。大規模差分は件数と条件をすべて表示して承認を求めます。
- 承認前にAction/Deleteを含む新規追加・削除・置換の全差分を表示し、Action/Delete・Trashのグループ承認後、最後の全体承認が得られた場合のみ変更します。未承認のグループはGmail現行状態を維持し、次の`run`で再提案します。Gmail APIで現在のフィルタを取得し、**旧ルールの削除→新ルールの追加**の順に読み戻し確認しながら変更します。
- API読戻し一致は**Gmail UIのfresh exportや新着メッセージの分類が完全であることの証明ではありません**。実配備後は必要に応じて別途検証してください。
- 2026-10-19の実配備は削除22件・追加0件で中断し、その後の診断では824件が承認済み計画の途中状態に一致しました。これは当時の記録です。今回の障害復旧処理は合成APIテストで検証しており、実Gmailでの改善後の配備完了は未確認です。再開時には現在の実設定と保留計画を照合してください。

依存ライブラリは`requirements.txt`を使用します。Dockerを使わない場合は`pip install -r requirements.txt`後に`python gmail_filter_deployer.py run`で同じCLIを呼べます（環境変数の設定が別途必要です）。

Gmail API公式資料：[Managing Filters](https://developers.google.com/workspace/gmail/api/guides/filter_settings) / [users.settings.filters](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.filters)。
