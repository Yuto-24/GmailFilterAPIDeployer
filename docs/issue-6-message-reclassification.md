# Issue #6: 既存メールの再分類・再開・復元

## 読取りバッチ

`--message-read-batch-size`は1〜50、既定1。複数件では最小メタデータのGETのみをHTTPバッチ化し、要求IDごとの全応答と重複なしを検証してから各メールの既存検証を行う。内側失敗の再試行も読取りのみで、毎秒20件を目安に間隔を空ける。計画、照合、送信直前、送信後で新規取得し、フェーズ間のキャッシュは使わない。更新件数、永続的な送信意図、更新の一回送信、各バッチのフィルタ照合は維持する。

## 対象と承認

追加オプション`run --reclassify-existing`は、起動時にアカウント・Masterハッシュ・置換方針・対象外ラベルを固定して承認を得て、メール用OAuthも配備前に済ませる。配備・対象フィルタ一致後のメール処理では、この実行中の承認を検証し、追加の対話なしで同じバックアップ・照合・送信手順を実行する。復元は含めない。既定の個別承認は以下のとおり。

`--skip-unknown-message-labels`を指定した計画は`gmail-message-reclassification/v2`。計画時に形式が正しいがラベル一覧にないIDを持つメールは、書込み対象から除き`plan.sqlite`の`deferred(id,metadata)`表に保存する。対象外と保留は別集計とし、保留ありは部分完了・終了コード4・進捗`complete=false`とする。対象行の照合完了は`eligible_verified=true`で記録し、保留を適用済みとは扱わない。未解決の送信意図がなければ保留ポインタを解消し、不整合解消後は新計画で確認する。復元は実際に変更した対象だけを扱う。指定なしのv1・通信失敗・メタデータ形式異常・計画後の競合は従来の停止条件を維持する。


`run`のフィルタ配備・読戻しが完了、または変更不要と確認された後、ユーザーラベルを付けるフィルタ群をMasterと照合する。一致した場合だけ準備確認を表示する。グループの見送り・配備中断などで不一致なら再分類を開始しない。`reclassify --plan-only`にも同じ照合を適用する。

準備の承諾後にメール用OAuth、全ページの列挙、バックアップ、検索を行う。対象・変更あり・変更なし・一致なし・複数一致・除外・新着・対象外ルール・未対応の件数と、ラベル別の解除／付与件数、バックアップ先、digestを表示する。未対応構文があれば計画全体を停止するため、確定した計画の未対応件数は0となる。更新は別の最終対話承認が必要。非対話では再分類・復元を開始しない。`--plan-only`は既存の有効な専用トークンで読取り計画を作成できる。

受信トレイとアーカイブ済みメールを対象にする。SENT・DRAFT・SPAM・TRASHを一つでも持つメール、およびメール以外のCHATは除外する。同じスレッドでもメッセージごとに判定する。手動分を含むユーザーラベルをMasterに一致するラベル集合へ置き換え、複数一致ならすべて付与、一致なしならユーザーラベルなしとする。システムラベル、本文、添付、ラベル定義は更新しない。ユーザーラベルを付けないTrashルールは集計上の対象外であり、既存メールをゴミ箱へ送らない。

## 検索用変換

PR #18の配備コンパイラ `xml-fields-v1` と比較正規化 `query-v2` は維持する。再分類専用の `message-search/v1` は、Gmailの検索結果をメッセージID集合として扱う。メール本文を取得・ローカル評価しない。

| 条件 | 検索と結合 |
|---|---|
| from | 単純送信者ORを個別の `from:` 検索の和集合へ。表示名などの複数語は送信者欄の引用フレーズ |
| to | 同じ値に対する `to:`・`cc:`・`bcc:` の和集合 |
| subject | 通常の複数語は件名の引用フレーズ。引用句を保持。平坦な `{語 "引用句"}` は個別件名検索の和集合 |
| hasTheWord | 現行コンパイラが作るqueryをそのまま検索 |
| doesNotHaveTheWord | 元の検索式の一致IDを集合から除外。否定構文への書換えなし |

条件欄同士は積集合で結合する。同じ検索式は実行内でキャッシュし、保存対象IDとの積集合だけを記録する。全ルールの結果を変更開始前に固定するので、`label:`や`is:unread`等も途中のラベル変更に影響されない。再開・復元では再検索・再コンパイルしない。

native欄は単純なアドレス・送信者OR・表示名・件名フレーズ・引用句・平坦な件名OR群に限定する。括弧・引用符の不整合、入れ子の件名OR、native欄への検索演算子注入、未対応の組合せやエスケープはメール変更前に拒否する。query/negatedQueryでは括弧・引用符の整合を検査するが、Gmail検索言語全体を独自に解釈しない。

件名ORは現Master内で同じ条件が `subject:{…}` としても使用されていることから採用した設計判断であり、任意のnativeフィルタ条件と検索の同等性を保証しない。現在の930ルールについてユーザーラベル用929ルールの構文対応をローカルで確認し、残るラベルなしTrashルール1件を対象外としている。実Masterの条件原文を公開fixtureへ転記していない。

根拠: [フィルタCriteria](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.filters#Criteria)、[検索演算子](https://support.google.com/mail/answer/7190?hl=en)。実メールでの検索結果確認は、合成データによる構文・集合演算の検証とは別に行う。

## 固定計画と進捗

`local/reclassification/<run-id>/`（所有者のみアクセス）に次を保存する。本文・添付は取得しないが、Master・条件・ラベル名・メールIDは非公開データなのでバックアップを公開しない。

| ファイル | 内容 |
|---|---|
| master.xml | 使用したMasterのコピー。条件原文を保持 |
| plan.sqlite | 対象ID、threadId、元の全ラベル、変更後ユーザーラベル、各ルールと検索式、検索一致ID、ルール一致ID |
| manifest.json | アカウント、方式バージョン、開始履歴位置、ラベルID・名前・種別、件数、固定ファイルのSHA-256、manifestのdigest |
| progress.sqlite | 承認、送信予定、メッセージ単位の進捗、読戻し結果を表す状態、失敗・競合イベント |

固定ファイルと進捗DBを分離する。計画ファイルのハッシュ、manifest、SQLite完全性、対象件数、進捗と送信予定の整合を検査する。送信予定はSQLite `synchronous=FULL` でコミットしてから送る。承認待ちの後にも固定ファイルと実メールを再検査する。`run`・`apply`・メール操作は同じ `local/run.lock` を使い、未完了メール更新があれば新しいフィルタ配備を止める。

最初の全ID列挙直前に `getProfile.historyId` を保存する。全ページ取得後、履歴で開始後の新着IDを除き、対象の最小メタデータを取得する。検索完了後に全IDを再列挙し、開始位置からの全履歴と比較する。開始後の新着は次回へ回す。既存メールの変更・削除、ID集合の不整合、ラベル定義・対象フィルタの変更、履歴期限切れ・読取り失敗は計画確定を停止する。現在の実装は対象外メールを含む既存メールの履歴変更にも保守的に停止する。

## 送信・再開・復元

変更前ユーザーラベルをU、変更後をDとして、解除 `U − D` と追加 `D − U` を同じ `messages.batchModify` に含める。同じ差分をまとめ、既定50メッセージずつ送る。共通ラベルは保持し、全メールを先に無ラベルにする工程はない。API仕様の上限は1000メッセージで、CLIも1〜1000に制限する。[batchModify仕様](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/batchModify)

各送信前に対象メール、ラベル定義、再分類では対象フィルタも照合する。計画確定後に作られた新規ユーザーラベル定義は、対象メールに付いていなければ再開・復元を妨げない。保存済み定義の変更・消失と、新規ラベルが対象メールに付与された場合は引き続き停止する。計画作成中は全ラベル定義の完全一致を要求する。送信後はバッチ全件の最小メタデータを読み戻し、ユーザーラベル一致と送信前からのシステム状態不変を確認する。最終的に対象全件を照合する。HTTP成功だけでは適用済みとしない。

読取りには既存の有界リトライを使用する。書込みはSDK・通信層とも自動再送しない。429・5xx・応答消失・中断は読戻しを試みて停止する。保存済み送信予定があるメールだけ、再開時に変更前／変更後と照合できる。反映済みなら再送せず、未反映だけを専用承認後に送る。第三の状態や読取り失敗は停止する。送信予定なしでたまたま変更後と同じになったメールを、この実行の成功とみなさない。

復元は送信予定と読戻しからこの実行による変更を確認できるメールだけを対象にする。現在のユーザーラベルが適用後と一致することを条件に、元のユーザーラベルへ戻す。現在の既読・スター・受信トレイ等のシステム状態は保持する。ユーザーラベルの外部変更、ラベル定義の変更・消失、SENT・DRAFT・SPAM・TRASH・CHATへの移動は競合として停止する。途中適用からの復元もでき、未変更メールには触れない。復元開始後に同じ計画の再分類へ戻すことはできない。

進捗は適用確認済み・未適用・不明・復元確認済みと、過去の競合検出累計を表示する。`verified=true` は当該モードの最終照合が完了した記録。拒否・バッチ上限停止を完了表示にしない。

Gmail側との排他、全メールの一括確定、読取り直後から送信までの無変更は保証しない。外部の変更が同じ結果になった場合に実行主体を完全に判別することもできない。操作中の他クライアントからのラベル編集は避け、検出した競合は強制上書きせず調査する。

## 検証と受入れ

合成Gmailではページ境界、1003メッセージ、同じスレッドの対象／除外混在、新着、外部変更、履歴期限切れ、バックアップ破損、非対話・承認拒否、OAuth不足・アカウント違い、部分反映、429/500、応答消失、送信前後の中断、再開・復元中断を検証する。実SDKでもネットワークを無効にして最小メタデータ取得とbatchModify要求の組立てを確認する。既存フィルタ計画v3〜v7のテストを含む全テストをSDK入り環境で実行する。

開発時のオフライン結果は[検証記録](reports/2026-10-27-issue-6-offline-validation.md)へ記録する。実Gmailでの初回計画・検索結果確認、実更新、実復元は別の受入れ工程であり、オフライン成功で代替しない。初回適用は完成した計画の件数と検索結果を確認してから行う。
