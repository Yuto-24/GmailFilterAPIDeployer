# Issue #6: 既存メールの再分類・再開・復元

## 時間の目安と再開

`--max-message-seconds`は有限の正数。起動時に期限を決め、完全な固定計画の作成後、適用前の照合と各更新バッチの区切りで確認する。計画作成は途中で切らず、送信済みバッチの読戻しも期限で打ち切らないため、指定時間を超える場合がある。起動時承認では照合前に承認記録・固定計画の保留ポインタを永続化し、期限到達後も同じ計画を再開する。保留は終了コード4で未完了として扱う。時間上限以外の適用エラーでは送信意図が一件もない場合だけ保留ポインタを解除し、固定バックアップと失敗記録を保持して再計画を可能にする。送信意図がある場合は解除しない。起動時に承認済みで追加の対話待ちがない場合は適用前の全件照合を重複実行せず、個別の対話承認では承認後にも再照合する。

## 読取りバッチ

`--message-read-batch-size`は1〜50、既定1。複数件では最小メタデータのGETのみをHTTPバッチ化し、要求IDごとの全応答と重複なしを検証してから各メールの既存検証を行う。内側失敗の再試行も読取りのみで、単独・複数件とも毎秒4件を目安に間隔を空ける（最小取得20単位、毎分4,800単位相当）。計画、送信直前、送信後は新規取得する。事前照合・承認後照合・最終照合では、下記の履歴確認付き進捗を再利用する。更新件数、永続的な送信意図、更新の一回送信、各バッチのフィルタ照合は維持する。

## 固定計画の照合再開（Issue #31）

PR #24で、最小メタデータのGETだけにHTTP 400 `failedPrecondition`の最大3回の再試行を追加した。恒久エラーや再試行上限で停止した場合も、固定計画を作り直さず、同じ `reclassify --resume RUN_ID`（復元は `restore-labels --run-id RUN_ID`）で再開する。

- 事前照合・承認後照合・最終照合で検証できたIDを `reconciliation.sqlite` に保存する。50件ごとと通常の例外終了時にコミットするため、強制終了時には未コミット分を再取得する。計画digest・適用/復元モード・送信予定と進捗状態が一致する記録だけを再利用する。
- 再利用前に `history.list` の全ページを確認し、変更された対象IDを無効にして未照合IDとともに取得する。無効化と履歴位置の更新は同じトランザクションで保存する。ラベル定義と対象フィルタは毎回確認する。対象外の新着メールを固定計画に追加しない。
- 各走査の直前に新しい履歴位置を取得し、走査末尾でもその区間を検査する。同じIDの再変更も再照合の対象となる。変更・履歴期限切れが続けば最大3走査で停止する。実際の状態が固定計画・送信予定に反する場合は従来どおり即停止し、メールを除外して続行しない。
- 履歴のHTTP 404は保存済み照合結果を破棄して全件照合に戻る。その他の履歴取得エラー、不正な応答、読取り失敗では停止する。期限切れからの全件同期は[Googleの同期仕様](https://developers.google.com/workspace/gmail/api/guides/sync)に従う。
- 対話承認後にも履歴と設定を確認する。変更のないメールの二度目の全件GETを省くが、承認自体は保存・再利用しない。再開する実行でも従来の承認が必要である。照合進捗だけでは `progress.sqlite` や送信予定を作らない。
- 新しい送信予定を記録する前に照合キャッシュを破棄する。更新直前・読戻しでは常に新しいGETを使い、書込み再送のルールは変更しない。既存v1/v2固定計画の再生成・移行は不要。最終照合には方式と段階を含む専用の照合証拠を使う。全変更が確認済みなら再承認を挟む照合もこの証拠を履歴で検証する。
- 例外停止には工程名と「この実行のラベル書込みは未開始／開始済み」を表示する。「未開始」は過去の実行でも未更新という意味ではない。過去の送信予定は引き続き保存進捗から照合する。

照合進捗は承認や保留ポインタとは別物である。送信予定がないエラーで保留ポインタを解除する既存の規則は維持するため、その場合の再開には保存したrun-idを明示する。チェックポイントを使わない旧版で実行した後も、送信予定・進捗が変わっていれば再利用しない。

回帰テスト: [test_reconciliation_checkpoint.py](../tests/test_reconciliation_checkpoint.py)。合成データで途中失敗、承認中の外部変更、履歴失効、ページ分割、カーソル更新直後の中断、同じIDの再変更、未承認・書込み後停止を検証する。

### 更新前のフィルタ整合性再照合

`filters.list` によるユーザーラベル用フィルタと固定計画Masterの比較は、完全一致が確認できた場合だけメール更新を継続する。APIの取得自体は成功したが比較結果が不一致だった場合に限り、30秒・60秒の待機を挟んで最大3回取得する。完全一致への回復時だけ継続し、3回とも不一致ならメール更新を停止する。API取得失敗・不正なフィルタ表現・未知のラベルIDを「一時的な不一致」と推定して継続しない。

発生した不一致の差分（Masterのみ・Gmailのみのルール、各回件数）は、`local/logs/diagnostics/message_filter_mismatch_*.json` に保存する。条件やラベルを含むため、公開Issueやコミットには添付しない。診断の保存失敗は警告を出すが、照合結果による停止・継続判断を変更しない。既存の固定計画、承認・送信前intent・進捗DB・メール状態保護は維持する。これはフィルタの外部編集を許可する仕組みではなく、Gmail APIの一時的な一覧不一致を再取得で確認する仕組みである。

## 対象と承認

追加オプション`run --reclassify-existing`は、起動時にアカウント・Masterハッシュ・置換方針・対象外ラベルを固定して承認を得て、メール用OAuthも配備前に済ませる。配備・対象フィルタ一致後のメール処理では、この実行中の承認を検証し、追加の対話なしで同じバックアップ・照合・送信手順を実行する。復元は含めない。既定の個別承認は以下のとおり。

`--skip-unknown-message-labels`を指定した計画は`gmail-message-reclassification/v2`。計画時に形式が正しいがラベル一覧にないIDを持つメールは、書込み対象から除き`plan.sqlite`の`deferred(id,metadata)`表に保存する。対象外と保留は別集計とし、保留ありは部分完了・終了コード4・進捗`complete=false`とする。対象行の照合完了は`eligible_verified=true`で記録し、保留を適用済みとは扱わない。未解決の送信意図がなければ保留ポインタを解消し、不整合解消後は新計画で確認する。復元は実際に変更した対象だけを扱う。指定なしのv1・通信失敗・メタデータ形式異常・計画後の競合は従来の停止条件を維持する。

`run`のフィルタ配備・読み戻しが完了した後、または変更不要と確認された後に、ユーザーラベルを付けるフィルタ群をMasterと照合する。一致した場合だけ準備確認を表示する。グループの見送りや配備中断などで不一致なら再分類を開始しない。`reclassify --plan-only`にも同じ照合を適用する。

- 準備を承諾すると、メール用OAuth、全ページの列挙、バックアップ、検索を行う。対象・変更あり・変更なし・一致なし・複数一致・除外・新着・対象外ルール・未対応の件数と、ラベル別の解除／付与件数、バックアップ先、digestを表示する。未対応構文があれば計画全体を停止するため、確定した計画の未対応件数は0となる。
- 実際の更新には、別の最終対話承認が必要である。非対話では再分類・復元を開始しない。`--plan-only`は既存の有効な専用トークンで読み取り計画を作成できる。
- 受信トレイとアーカイブ済みメールを対象にする。SENT・DRAFT・SPAM・TRASHを1つでも持つメール、およびメール以外のCHATは除外する。同じスレッドでもメッセージごとに判定する。手動分を含むユーザーラベルをMasterに一致するラベル集合へ置き換え、複数一致ならすべて付与、一致なしならユーザーラベルなしとする。システムラベル、本文、添付、ラベル定義は更新しない。ユーザーラベルを付けないTrashルールは集計上の対象外であり、既存メールをゴミ箱へ送らない。

## 検索用変換

PR #18の配備コンパイラ `xml-fields-v1` と比較正規化 `query-v2` は維持する。再分類専用の `message-search/v1` は、Gmailの検索結果をメッセージID集合として扱う。メール本文の取得やローカル評価は行わない。

| 条件 | 検索と結合 |
|---|---|
| from | 単純送信者ORを個別の `from:` 検索の和集合へ。表示名などの複数語は送信者欄の引用フレーズ |
| to | 同じ値に対する `to:`・`cc:`・`bcc:` の和集合 |
| subject | 通常の複数語は件名の引用フレーズ。引用句を保持。平坦な `{語 "引用句"}` は個別件名検索の和集合 |
| hasTheWord | 現行コンパイラが作るqueryをそのまま検索 |
| doesNotHaveTheWord | 元の検索式の一致IDを集合から除外。否定構文への書き換えなし |

- 条件欄同士は積集合で結合する。同じ検索式は実行内でキャッシュし、保存対象IDとの積集合だけを記録する。変更開始前に全ルールの結果を固定する。再分類で通常のシステムラベル差分があれば、保存した検索式を使い分類結果への影響を確認する。復元では再検索しない。
- native欄は、単純なアドレス・送信者OR・表示名・件名フレーズ・引用句・平坦な件名OR群に限定する。括弧・引用符の不整合、入れ子の件名OR、native欄への検索演算子の注入、未対応の組み合わせやエスケープはメール変更前に拒否する。query/negatedQueryでは括弧・引用符の整合を検査するが、Gmail検索言語全体を独自に解釈しない。
- 件名ORは、現Master内で同じ条件が `subject:{…}` としても使用されていることから採用した設計判断であり、任意のnativeフィルタ条件と検索の同等性を保証しない。現在の930ルールについてユーザーラベル用929ルールの構文対応をローカルで確認し、残るラベルなしTrashルール1件を対象外としている。実Masterの条件原文は公開fixtureへ転記していない。

根拠: [フィルタCriteria](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.filters#Criteria)、[検索演算子](https://support.google.com/mail/answer/7190?hl=en)。実メールでの検索結果確認は、合成データによる構文・集合演算の検証とは別に行う。

## 固定計画と進捗

`local/reclassification/<run-id>/`（所有者のみアクセス）に次を保存する。本文・添付は取得しないが、Master・条件・ラベル名・メールIDは非公開データなのでバックアップを公開しない。

| ファイル | 内容 |
|---|---|
| master.xml | 使用したMasterのコピー。条件原文を保持 |
| plan.sqlite | 対象ID、threadId、元の全ラベル、変更後ユーザーラベル、各ルールと検索式、検索一致ID、ルール一致ID |
| manifest.json | アカウント、方式バージョン、開始履歴位置、ラベルID・名前・種別、件数、固定ファイルのSHA-256、manifestのdigest |
| progress.sqlite | 承認、送信予定、メッセージ単位の進捗、読み戻し結果を表す状態、失敗・競合イベント |
| reconciliation.sqlite | 事前・承認後照合の検証済みID、履歴位置、固定計画・送信進捗との対応。承認や送信記録ではない |

- 計画を固定するファイルと、更新する進捗DBを分離する。計画ファイルのハッシュ、manifest、SQLite完全性、対象件数、進捗と送信予定の整合を検査する。送信予定はSQLite `synchronous=FULL` でコミットしてから送る。承認待ちの後にも固定ファイルと実メールを再検査する。`run`・`apply`・メール操作は同じ `local/run.lock` を使い、未完了メール更新があれば新しいフィルタ配備を止める。
- 計画作成はPR #30のチェックポイントv2を使用する。最初の列挙直前の `getProfile.historyId` と対象を保存し、新着を除外する。既存メールの変更は差分を再取得し、明示的な削除履歴があるIDだけを除く。変化し得る検索条件も再評価し、分類・検索一致・件数を整合させてから固定する。対象外メールの対象入り、説明できない欠落、ラベル定義・対象フィルタの不一致、履歴期限切れなどは停止する。固定計画の適用前照合とは異なる工程であり、詳細は[計画作成の知識エントリ](knowledge/entries/message-planning-consistency.md)を参照する。

## 送信・再開・復元

- 変更前ユーザーラベルをU、変更後をDとして、解除 `U − D` と追加 `D − U` を同じ `messages.batchModify` に含める。同じ差分をまとめ、既定50メッセージずつ送る。共通ラベルは保持し、全メールを先に無ラベルにする工程はない。API仕様の上限は1000メッセージで、CLIも1〜1000に制限する。[batchModify仕様](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/batchModify)
- 各送信前に対象メール、ラベル定義、および再分類では対象フィルタも照合する。計画確定後に作られた新規ユーザーラベル定義は、対象メールに付いていなければ復元を妨げない。再分類の再開では、この条件に加え、Gmailのフィルタが新規ラベルIDを使用していないことも必要である。保存済み定義の変更・消失と、新規ラベルが対象メールに付与された場合は引き続き停止する。計画作成中は全ラベル定義の完全一致を要求する。送信後はバッチ全件の最小メタデータを読み戻し、ユーザーラベルの一致を確認する。復元中は送信前からのシステム状態も照合する。再分類中に通常のシステムラベルが変化した場合は、固定計画の検索結果と、状態に依存する条件についてGmailが返す現在の該当IDから、ユーザーラベルの集合を再照合する。自身の書込み後に任意の検索式の影響を分離できない場合は停止する。最終的に対象全件を照合する。HTTP成功だけでは適用済みとしない。
- 読み取りには既存の有界リトライを使用する。書き込みはSDK・通信層とも自動再送しない。429・5xx・応答消失・中断は読み戻しを試みて停止する。保存済み送信予定があるメールだけ、再開時に変更前／変更後と照合できる。反映済みなら再送せず、未反映だけを専用承認後に送る。第三の状態や読み取り失敗は停止する。送信予定なしでたまたま変更後と同じになったメールを、この実行の成功とみなさない。
- 復元は、送信予定と読み戻しからこの実行による変更を確認できるメールだけを対象にする。現在のユーザーラベルが適用後と一致することを条件に、元のユーザーラベルへ戻す。現在の既読・スター・受信トレイ等のシステム状態は保持する。ユーザーラベルの外部変更、ラベル定義の変更・消失、SENT・DRAFT・SPAM・TRASH・CHATへの移動は競合として停止する。途中適用からの復元もでき、未変更メールには触れない。復元開始後に同じ計画の再分類へ戻すことはできない。
- 進捗は、適用確認済み・未適用・不明・復元確認済みと、過去の競合検出累計を表示する。`verified=true` は当該モードの最終照合が完了した記録である。拒否・バッチ上限停止を完了表示にしない。

Gmail側との排他、全メールの一括確定、読み取り直後から送信までの無変更は保証しない。外部の変更が同じ結果になった場合に実行主体を完全に判別することもできない。操作中の他クライアントからのラベル編集は避け、検出した競合は強制上書きせず調査する。

## 検証と受入れ

合成Gmailでは、ページ境界、1003メッセージ、同じスレッドの対象／除外混在、新着、外部変更、履歴期限切れ、バックアップ破損、非対話・承認拒否、OAuth不足・アカウント違い、部分反映、429/500、応答消失、送信前後の中断、再開・復元中断を検証する。実SDKでもネットワークを無効にして、最小メタデータ取得とbatchModify要求の組み立てを確認する。既存フィルタ計画v3〜v7のテストを含む全テストをSDK入り環境で実行する。

開発時のオフライン結果は[検証記録](reports/2026-10-27-issue-6-offline-validation.md)へ記録する。実Gmailでの初回計画・検索結果確認、実更新、実復元は別の受け入れ工程であり、オフライン成功で代替しない。初回適用は完成した計画の件数と検索結果を確認してから行う。
